# 实施、修复与最终交付

## 阶段实施

1. 确认用户指定阶段与验收条件，检查已有改动，不从零重做已完成内容。
2. 沿用现有实现、结构和依赖，只完成当前阶段所需代码、测试及文档。
3. 按项目规范执行相关检查；检查自动修复产生的差异，影响行为或类型时复验相关内容。
4. 检查 git diff、暂存区和未跟踪文件，确认必要文件齐全，没有范围外内容。
5. 报告交付与验收条件的对应关系、主要文件及目的、检查命令和结果、限制和剩余事项。

实施中不修改 PLAN.md。发现关键计划错误时提出最小修订方案；不默默扩大范围。若用户已明确授权修订计划，可在授权范围内更新并说明。

完成指定阶段后停止；存在跨阶段授权时继续其覆盖的工作。没有 Git 仓库时说明 Git 检查不适用，不仅为完成流程执行 git init。

## 针对性修复

只处理已核实的必须修复项，以及用户接受的可选建议。审查报告本身不是要求执行所有建议的授权。

先确认问题成立；不成立或有冲突的事项给出证据。采用最小合理修改，不顺手重构。

修复行为缺陷时，必要的回归测试应能暴露原缺陷并验证修复。重跑失败用例及受影响的检查；不机械运行所有测试。

逐项更新问题编号、修改方式、验证结果和剩余原因。交给复审的项目标为待复验，不能因为修改完成就标记全部关闭。

## 最终验收与收尾

对照计划逐项核实交付物，区分完成、未完成、受阻和未验证。完成收尾不是默认接受未完成项。

检查并补齐必要文档：

- 新项目说明安装运行、核心设计和工作流、测试方式、关键假设及限制。
- 已有项目只更新受影响内容；详细架构和开发说明沿用原位置，README 可链接，不复制。
- 初始化后补充 AGENTS.md 的真实目录和命令时，核实它们确实存在；不添加未经确认的新团队规则。

按项目约定执行最终完整测试和静态检查，遵循其顺序及复用规则。完整范围以实际脚本和计划为依据，不虚构统一入口。外部凭据、网络、特定系统、浏览器、真实硬件等验收条件单独说明，不将跳过当通过。

发现交付缺陷时，仅修复授权范围内的必要问题并针对性复验；不新增功能或无关重构。

最后核对 git status、提交差异、暂存区、未暂存和新增文件；列出本次应提交的内容和应排除的过程产物，不自动清理用户文件。

交付报告包含：

- 验收结论及交付物。
- 本轮执行和复用的检查、结果及覆盖范围。
- 本次问题、原有问题、环境限制与未验证项。
- 建议提交的文件和简洁的提交说明或 PR 描述草稿（需要时）。

## Git 与发布边界

最终验收不自动触发 commit、push、PR、发布或部署。用户授权后，仅执行被授权操作；例如同意提交不等于同意推送或部署。

提交时只纳入任务文件，避免通过批量暂存夹带用户其他工作。已有有效授权无需再次询问；遇到范围外风险先说明。
