# WQ-workflow

帮助用户完成可验收、方便协作者维护的交付。用户可能不熟悉项目结构；解释具体影响和理由，不以术语、文档数量或检查次数代替质量。

## 入口与阶段选择

先读取适用的 AGENTS.md、用户指定计划和必要的项目事实；不要无差别遍历全部文档。已有项目保留其语言、结构、依赖和命令；没有代码的新项目从需求澄清开始。

从用户当前请求和已有记录确定本轮模式，不要求用户重复确认已明确的信息：

| 用户意图 | 本轮工作 | 按需读取 |
| --- | --- | --- |
| 从想法出发、头脑风暴、质询需求、生成或修订计划 | 澄清影响方案的决定，形成可验收计划 | [规划](references/planning.md) |
| 审查计划 | 检查可行性、遗漏和过度设计，不修改实现 | [审查](references/review.md) |
| 实现某阶段、修复已确认的问题 | 完成授权范围并验证 | [实施与交付](references/delivery.md) |
| 审查代码、复审修复 | 找有依据的缺陷和交付问题 | [审查](references/review.md) |
| 最终验收、补齐交付物、收尾 | 核对完成情况、必要文档和整体检查 | [实施与交付](references/delivery.md) |

默认完成本轮指定环节后停止并报告下一步，不自动从审查转为修改，也不自动实施所有计划阶段。用户明确授权连续执行多个环节时，可在该范围内继续；重大需求取舍仍需确认。

文案、小型配置或已明确的局部修复可以直接实施并检查，不强制补齐计划和全部环节。多模块或高不确定性任务使用完整流程。独立审查只有在实际由另一 agent 完成时才这样称呼；用户要求另一个 agent 审查时，在可用且获准的情况下委派，否则说明限制，不冒充独立审查。

## 跨项目约束

- 当前用户要求和项目明确约定优先于本技能的默认偏好。发现实质冲突时说明影响，不将个人偏好写成团队规定。
- 先识别已有工作区改动，不覆盖、删除、还原、暂存或提交不属于本轮的内容。
- 以验收目标控制范围。不添加未要求的功能、UI、数据库、服务或复杂框架；不要为了未来可能的需求创建抽象。
- 不将示例领域固化为通用要求。仅在项目采用 Python 时优先标准库和已有依赖。
- 低风险且可逆的细节可自行决定；影响目标、兼容性、数据安全或验收标准的歧义先列选项和影响，必要时询问用户。
- Git commit、push、创建 PR、发布及部署均需用户明确授权；既有授权继续有效，只执行其覆盖的操作。阶段验收通过本身不构成授权。
- 修改共享业务代码或规则之前检查当前阶段权限。计划阶段不写业务代码；实施与审查阶段不擅自修改 PLAN.md；审查阶段不运行会修改文件的自动修复命令。

## 验证证据与检查复用

每次交接保留：执行命令及目录、检查范围、结果、相关代码状态、未验证项。区分本轮执行与复用旧结果。

只在相关代码、测试、配置、依赖或环境未发生影响结果的变化，且能核对已有记录时复用。HEAD 相同不足以证明未提交改动相同；必要时用相关差异或文件指纹核对。记录缺失或无法判断时，重跑最小相关检查。

实施跑阶段相关检查；审查按新发现补充；修复跑失败用例和影响范围；最终收尾按项目规范执行完整检查。已经有效覆盖最终状态的结果可复用，项目明确要求重跑则遵守。不能用检查复用来跳过未覆盖的风险。

测试围绕可观察行为、边界、失败路径和验收条件。不为可逆的小改动凑测试，不仅从实现生成期望值。避免锁死与需求无关的数量、顺序、可选字段缺失或措辞；如果这些本身是契约，则应断言。

软件测试通过不等于浏览器交互、外部服务、真实硬件或生产环境已验收。明确标识失败、跳过、受阻及未执行，不将局部通过描述为全仓通过。

## 文档与交接

- AGENTS.md：已确认的长期项目规则和真实操作指引。
- PLAN.md：当前任务的范围、假设、阶段、交付物和验收条件；已有其他计划格式时沿用。
- README / 开发文档：使用与开发所需说明，只更新受影响内容。
- 审查记录：沿用一份问题记录，保留编号与状态，不逐轮制造新文件。

记录位置遵循用户或仓库约定。没有文件输出要求时，在回复中提供交接；需要文档但未指定位置时，优先采用已有目录，避免覆盖已有内容，并说明选择。不要默认把个人过程记录纳入团队提交。

每轮简洁汇报：完成内容、证据、剩余问题和下一步。不重复整套流程，不因为仍有可选建议就阻止验收。
