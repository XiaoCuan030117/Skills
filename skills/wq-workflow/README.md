# WQ-workflow

一套用于 Codex 的个人项目开发技能，将需求澄清、计划、实现、审查、修复和交付组织成可复用的工作流程。

它帮助开发者控制任务范围、保留验证依据，并让改动便于协作者理解和维护。既适用于从零开始的项目，也适用于已有项目中的功能开发和局部修复。

- **显示名称**：WQ-workflow
- **技能标识**：`wq-workflow`
- **显式调用**：`$wq-workflow`
- **规则入口**：[SKILL.md](SKILL.md)
- **仓库**：[XiaoCuan030117/Skills](https://github.com/XiaoCuan030117/Skills)

## 用途与边界

适合用于：

- 将一个想法澄清为可执行、可验收的计划。
- 按 `PLAN.md` 完成指定阶段。
- 审查计划或代码中的遗漏、错误和过度设计。
- 根据审查结果进行针对性修复和复验。
- 最终核对交付物、文档、测试及已知限制。

技能不绑定某个项目、语言或框架，会优先沿用项目已有结构、依赖和 `AGENTS.md` 约定。小型文案、配置修改或明确的局部修复可以简化为实施与检查，不必完整走遍所有环节。

它是一组给 agent 的工作指引，不是自动运行的工作流引擎，也不是强制权限控制。不会因为安装技能就自动开发项目、创建多个 agent 或持续运行。提交、推送、PR、发布和部署仍需要用户明确授权。

## 安装

这是一个以说明文件为主的技能，无需安装 Python、Node.js 或额外运行依赖。实际开发和测试所需环境由目标项目决定。

### 使用 Codex 技能安装器

如果当前环境提供 `$skill-installer`，可在 Codex 中输入：

```text
使用 $skill-installer，从以下地址安装 wq-workflow：
https://github.com/XiaoCuan030117/Skills/tree/main/skills/wq-workflow
```

安装器的目标目录以当前环境配置为准。已有同名技能时，先确认要保留或更新哪一份，避免重复安装或直接覆盖自定义修改。

### 手动个人安装：供多个项目使用

1. 从 [Skills 仓库](https://github.com/XiaoCuan030117/Skills) 下载 ZIP 并解压。
2. 找到其中的 `skills/wq-workflow/`，确认直接包含 `SKILL.md`、`agents/` 和 `references/`。
3. 将完整的 `wq-workflow` 文件夹放入个人技能目录；不要将整个 Skills 仓库当成单个技能安装。

当前 Codex 官方文档列出的个人技能目录是：

```text
~/.agents/skills/wq-workflow/
```

部分现有环境使用 `~/.codex/skills/`。如果你的 Codex 已在该目录发现个人技能，可沿用实际使用的目录。选择一个被当前环境识别的位置，避免在多个可发现目录中安装同名副本。

安装后应当直接存在：

```text
<个人技能目录>/wq-workflow/SKILL.md
```

不要多套一层同名目录，也不要只复制 `SKILL.md` 而遗漏引用文件。

### 项目安装：供一个项目使用

将同一份技能目录放入项目根目录下的：

```text
.agents/skills/wq-workflow/
```

如果准备将技能随团队项目提交，先确认符合团队约定。个人使用时优先采用个人安装，避免把自己的流程直接加入团队仓库。

### 确认安装

在 Codex 中选择或输入 `$wq-workflow`，要求它读取技能并说明可用环节。若未显示，重启 Codex 后重试。

Codex 支持显式调用和根据描述自动匹配技能。希望明确采用这套流程时，建议显式写出 `$wq-workflow`。目录发现和调用方式以 [Codex 官方技能文档](https://learn.chatgpt.com/docs/build-skills) 为准；其他 agent 工具的安装位置和调用方式可能不同。

## 调用示例

以下示例按环节分别使用，不需要一次全部发送。补充实际需求、阶段编号及审查范围即可。

### 1. 从想法到计划

```text
使用 $wq-workflow。
我想做一个本地文件整理工具，先帮我质询需求，明确目标、约束和非目标。
需求及初始方案明确后，创建简版 AGENTS.md 和 PLAN.md。
计划按可独立验收的阶段拆分。本轮不写业务代码，完成计划后停止。
```

已有项目中，优先读取现有 `AGENTS.md`，不要求重建。新项目还没有确定的目录或命令时，不编造内容；初始化后再补充真实信息。

### 2. 审查计划

```text
使用 $wq-workflow，阅读项目约定和 PLAN.md，
检查可行性、明显遗漏、阶段验收方式和过度设计。
区分必须调整、可选建议和待确认事项。本轮只报告，不修改文件。
```

如需独立审查，可以在另一个 agent 或聊天中使用这段提示词，并提供相同计划、需求和项目访问条件。技能本身不会保证自动产生独立审查者。

### 3. 实现阶段

```text
使用 $wq-workflow，按照 PLAN.md 完成第一阶段。
沿用现有结构和依赖，不扩大范围，不修改 PLAN.md。
完成必要代码和测试，执行相关检查，汇报结果和限制后停止。
不提交、不推送、不创建 PR。
```

### 4. 审查实现

```text
使用 $wq-workflow，审查当前阶段的改动。
先说明比较基线，并检查相关提交、暂存、未暂存和未跟踪文件。
核对实现阶段的验证记录，仅补充必要检查。
区分必须修复、可选建议和待确认事项；只报告，不修改代码。
```

如需保存报告，指定现有文档位置或要求选择合适的位置；后续沿用同一份记录更新问题状态。审查结果可以直接留在回复中，不必每轮创建文件。

### 5. 修复与复审

```text
使用 $wq-workflow，修复审查记录中已确认的必须修复项。
可选建议暂不处理，不做无关重构。
运行受影响的检查，逐项汇报处理方式和验证结果后停止。
```

随后向审查者发送：

```text
使用 $wq-workflow，复审上一轮问题是否解决，
并检查修复是否引入新问题。除非出现新证据或范围扩大，
不重新展开整轮审查，也不将可选建议升级为阻碍。
```

### 6. 最终验收

```text
使用 $wq-workflow，对照 PLAN.md 完成最终验收和收尾。
核对交付物，只补充必要的 README 或开发文档，
按项目规范完成最终测试和静态检查，检查文件及差异。
报告完成情况、检查结果、已知限制和建议提交的内容。
不新增功能，不做无关重构，不提交、不推送、不创建 PR。
```

## 工作流程

```text
需求澄清 → 制定计划 → 审查计划
                         ↓
                 实现指定阶段
                         ↓
                 审查 → 必要修复 → 针对性复审
                         ↓
              阶段验收 → 下一阶段或最终验收
                         ↓
               用户授权后执行对应 Git / 发布操作
```

默认完成当前指定环节后停止。用户可以明确授权连续执行多个环节；已有有效授权不需要反复确认。重大需求取舍或范围变化仍需说明并确认。

| 环节 | 主要结果 | 结束条件 |
| --- | --- | --- |
| 需求澄清与计划 | 明确假设、范围、阶段、交付物和验证方式 | 能开始第一阶段，关键阻碍已明确 |
| 计划审查 | 有依据的遗漏、风险和最小调整建议 | 没有阻碍执行的未决问题 |
| 阶段实施 | 代码、必要测试及验证记录 | 当前阶段验收条件满足 |
| 审查与修复 | 稳定编号的问题及处理状态 | 必须修复项解决，或用户明确接受剩余风险，且验收条件满足 |
| 最终验收 | 完整交付说明、文档和检查结果 | 完成情况与限制清楚，未完成项没有被隐藏 |

## 减少重复工作

- **检查复用有依据**：已有结果只有在相关代码、测试、配置、依赖及环境没有影响结果的变化时才复用；记录不足则补跑。相同提交号不代表未提交内容相同。
- **测试按影响范围执行**：实施验证阶段目标，修复验证失败用例及影响范围，最终按项目规范完成整体检查。
- **建议不自动变成任务**：可选建议由用户决定是否接受，不以“再也提不出建议”为验收条件。
- **复审聚焦变化**：优先检查上轮问题及修复影响，出现新证据时再扩展范围。
- **文档各司其职**：长期规则放 `AGENTS.md`，当前任务放计划，使用说明放 README 或开发文档；避免复制同一份内容。

## 文件结构

```text
wq-workflow/
├── SKILL.md
├── README.md
├── agents/
│   └── openai.yaml
└── references/
    ├── planning.md
    ├── review.md
    └── delivery.md
```

- [SKILL.md](SKILL.md)：阶段选择、通用边界、验证证据和交接规则。
- [planning.md](references/planning.md)：需求质询、初始项目规则和计划编写。
- [review.md](references/review.md)：计划审查、代码审查、问题记录和复审。
- [delivery.md](references/delivery.md)：实施、修复、收尾及 Git 操作边界。
- [openai.yaml](agents/openai.yaml)：技能在 Codex 中的显示信息。

## 限制与维护

- 技能不替代项目自身规范、安全控制、CI 或人的判断。
- 不强依赖其他质询或审查技能；用户明确调用其他技能时，按其实际可用性配合使用。
- 软件测试通过不能代表真实硬件、浏览器交互、外部服务或生产环境已验收。
- 当前已完成格式、元数据及文件引用的静态检查，尚未完成真实项目全流程验证。
- 后续根据实际使用中出现的问题做小范围调整，优先修正规则歧义，避免不断增加通用限制。
